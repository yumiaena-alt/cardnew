# 인스타툰 파이프라인

> 벤치마킹으로 뽑은 전개 공식 + 고정된 주인공 → 컷별 스토리보드 → 컷마다 그린 그림 → 말풍선 합성 → 덱.
>
> 카드뉴스 파이프라인([`02-ARCHITECTURE.md`](02-ARCHITECTURE.md) §5-2)과 **같은 자리에 서고 같은 것을 내놓는다.**
> 다른 것은 가운데 두 단계뿐이다: 카피 대신 스토리보드를 쓰고, 사진을 찾는 대신 그림을 그린다.

---

## 1. 왜 카드뉴스와 한 파이프라인인가

인스타툰을 별도 실행 경로로 만들지 않았다. 결과물이 **덱 하나와 패널 여러 장**으로 같기 때문이다.
같은 모양으로 끝나면 뒤에 붙은 것이 전부 그대로 따라온다.

| 이미 있는 것 | 인스타툰이 물려받는 방식 |
|---|---|
| 캔버스 편집기 | 패널의 `doc`(SlideDoc)을 그대로 연다. 말풍선은 도형+텍스트 두 레이어라 드래그·색·크기가 바로 동작 |
| Dry-run 견적 | `estimateRun`이 `mode`를 보고 단가를 고른다. 차감 경로는 하나뿐 |
| 부분 실패 환불 | `run_items` 행 단위. 안 나온 것만 환불 |
| 예약 발행 · 릴스 · 성과 | 덱을 보므로 인스타툰인지 카드뉴스인지 알 필요가 없다 |

그래서 새로 만든 것은 `run_items.mode` 컬럼 하나와, 그 값이 `toon`일 때 타는 갈래 하나다.

```
src/trigger/generateRun.ts  →  mode === 'toon' ? generateToonCut() : generateCut()
```

## 3. 1단계 — 벤치마킹 분석

### 무엇을 가져오고 무엇을 안 가져오는가

이 단계 프롬프트의 절반은 **가져오지 말라는 지시**다. 구조는 관찰이고 표현은 저작물이다 —
그 경계를 모델에게 맡기면 대사를 요약해서 돌려준다.

| 가져온다 (구조) | 안 가져온다 (표현) |
|---|---|
| 컷 수, 컷별 역할 | 대사·나레이션 원문, 살짝 바꾼 문장 |
| 긴장도 곡선 (컷별 1~5) | 등장인물 이름·직업·관계 |
| 후킹 문구의 **골격** | 구체적인 사건과 소재 |
| 말투·분위기 태그 | 그림체·색·컷 분할 |

### 세 겹의 저작권 가드레일

1. **프롬프트** — 좋은 예/나쁜 예를 함께 준다. 금지만 하면 같은 실수를 반복한다.
   ```
   ✗ hookPattern: "3년을 일했는데 퇴직금이 없다고 합니다"   (원문을 옮긴 문장)
   ✓ hookPattern: "근속 기간 + 못 받은 돈을 첫 줄에"
   ```
2. **스키마** — 후킹 패턴은 40자 상한이다. 원문 한 줄이 그대로 들어갈 수 없는 길이로
   묶어 두면 모델이 베끼려 해도 패턴으로 요약할 수밖에 없다.
3. **코드 검사** — `findVerbatimRisk()`가 종결어미로 끝나는 패턴을 잡아 경고로 올린다.
   상한 안에서도 캡션 한 줄이 그대로 들어올 수 있고, 그럴 때는 대개 패턴 서술이 아니라 완결된 문장이다.
   하드 실패로 두지 않는다 — 판별이 완벽하지 않고, 확인할 수 있는 사람은 레퍼런스를 올린 본인이다.

**레퍼런스 이미지는 저장하지 않는다.** 디자인 학습(`design_learnings`)과 같은 이유로 장수만 남긴다.
`rights_confirmed_at`은 남긴다 — 남의 콘텐츠를 분석에 넣었다는 사실과, 그래도 된다고 누군가
확인했다는 사실이 함께 남아야 한다.

## 4. 2단계 — 스토리보드 (LLM 계약)

### 시스템 프롬프트가 지키는 다섯 가지

전문: [`src/lib/toon/prompts/storyboard-prompt.ts`](../src/lib/toon/prompts/storyboard-prompt.ts)

1. 모델은 **무엇을 말하고 무엇을 그릴지**만 쓴다. 좌표·색·폰트는 요구하지 않는다.
2. 글자수 상한을 **이유와 함께** 준다. 이유가 없으면 모델이 자주 넘긴다.
3. 장면 역할 흐름을 지정한다. 자유롭게 두면 9컷 중 6컷이 갈등이 되어 사이다가 오지 않는다.
4. **인물의 생김새를 쓰지 못하게 막는다.** 캐릭터 앵커의 몫이고, 컷마다 다시 묘사하면
   그 묘사가 흔들린 만큼 얼굴이 바뀐다.
5. 나쁜 예를 함께 보여준다.

가장 중요한 한 대목:

```
✗ imagePrompt: "a woman in her 20s with short black hair, wearing a beige knit,
                sitting at a cafe table"
✓ imagePrompt: "sitting across a cafe table from an older manager, shoulders
                drawn in, cold morning light from the left, medium shot"
```

그리고 배경 소품에 글자를 넣지 말라는 지시. 간판·메뉴판·휴대폰 화면을 묘사하면 모델이 글자를
그리려 들고, 그 위에 말풍선을 얹으면 둘 다 안 읽힌다.

### Response Schema

`generateText({ output: Output.object({ schema: toonStoryboardSchema }) })`로 강제한다.
스키마 위반은 도구 호출 레이어에서 잡히므로 모델이 스스로 재시도한다.

```ts
ToonStoryboard = {
  cuts: ToonCut[],          // ← 반드시 첫 필드. 필드 순서가 곧 생성 순서다
  hook: string,             // ≤ 60자
  logline: string,          // ≤ 120자
  caption: string,          // ≤ 2000자
  hashtags: string[],
}

ToonCut = {
  cutNumber: 1..10,
  sceneType: 'cover' | 'setup' | 'conflict' | 'climax' | 'resolution' | 'cta',
  imagePrompt: string,      // 영문, ≤ 400자. 장면만 — 외모 금지
  characterEmotion: string, // 영문 표정 태그
  narration: string | null, // 한글 ≤ 48자  (그림 위 흰 띠 한 줄)
  dialogue: [{              // 최대 3개
    speaker: string,
    text: string,           // 한글 ≤ 24자  (말풍선 폭 42%에 2줄이 한계)
    anchor: 'top-left' | 'top-right' | 'middle-left' |
            'middle-right' | 'bottom-left' | 'bottom-right',
    tone: 'speech' | 'thought' | 'shout' | 'whisper',
  }],
  visualFocus: string | null, // 표지 전용, ≤ 20자
}
```

**상한의 근거는 실측이다.** 대사 24자는 4:5 캔버스에서 말풍선 폭 42%(453px)에 한글 2줄,
글자당 약 36px → 줄당 12자. 나레이션 48자는 흰 띠 한 줄에 들어가는 양.
넘치면 조판이 줄여 주는 게 아니라 **그림을 가린다** — 카드뉴스 제목과 다른 점이다.

### 장면 역할 흐름

공식이 없으면 `defaultSceneFlow(n)`이 뼈대를 잡는다. 갈등이 절반을 넘으면 답답하기만 하고,
없으면 반전이 싱겁다. 중간을 2:1로 나눈다.

```
9컷:  cover · setup · conflict×4 · climax×2 · resolution · cta
```

## 5. 3단계 — 캐릭터 일관성

인스타툰이 카드뉴스와 갈라지는 지점은 여기 하나다: **1컷과 9컷의 주인공이 같은 사람으로 보여야 한다.**
이미지 모델은 같은 프롬프트에도 매번 다른 얼굴을 만든다. 그래서 일관성은 모델에게 부탁할 게 아니라
**입력을 고정해서** 얻는다.

### 세 겹 — 위에서부터 강한 순

| 장치 | 무엇인가 | 없으면 |
|---|---|---|
| **① 참고 이미지** | 캐릭터 시트 한 장을 매 컷에 image-to-image로 함께 넣는다 (`strength 0.65`) | 아래 둘만으로도 동작한다. 대신 얼굴이 더 흔들린다 |
| **② 앵커 프롬프트** | 생김새 문장을 **한 번 만들어 저장**하고 매 컷 맨 앞에 글자 그대로 붙인다 | 컷마다 모델이 외모를 다시 묘사하고, 흔들린 만큼 얼굴이 바뀐다 |
| **③ 고정 시드** | 같은 캐릭터의 모든 컷이 같은 시드를 쓴다 | 구도뿐 아니라 화풍과 인상까지 컷마다 달라진다 |

`strength 0.65`는 "같은 인물, 다른 장면"이 나오는 값이다. 더 낮추면 컷마다 같은 포즈가 나오고,
더 올리면 얼굴이 흔들리기 시작한다.

### 앵커를 왜 저장하는가

`toon_characters.anchor_prompt`는 생성해서 **컬럼에 넣는다.** 생김새 항목에서 매번 다시 조립하면
항목 하나를 고쳤을 때 과거 덱까지 다른 인물이 되고, 그게 언제 바뀌었는지 아무도 모른다.
저장해 두면 "캐릭터를 고쳤다"가 명시적인 행동이 된다.

### 순서가 중요하다

```ts
buildCutPrompt() =
  [앵커]                          ← 먼저
  "Scene: " + imagePrompt         ← 나중
  "Expression: " + emotion
  "No text, no lettering, no speech bubbles anywhere in the image."
  "Leave uncluttered negative space in the upper third for later captioning."
```

이미지 모델은 앞쪽 토큰에 더 큰 가중치를 준다. 장면을 앞에 두면 컷마다 인물이 장면에 끌려간다.

마지막 두 줄이 4단계와 맺은 계약이다. 말풍선이 얹힐 자리를 프롬프트가 미리 비워 두지 않으면,
조판이 아무리 잘 피해도 인물이 프레임을 꽉 채운 컷에서는 가릴 곳밖에 남지 않는다.

### 네거티브 프롬프트

맨 앞 세 항목이 이 파이프라인의 전제다.

```
text, letters, korean characters, speech bubble, watermark, signature, logo,
extra fingers, deformed hands, extra limbs, blurry, photorealistic, nsfw
```

### 시드

- 첫 시도는 캐릭터 시드 그대로.
- 재시도(`attempt > 0`)일 때만 소수 보폭으로 옮긴다. 같은 시드로 다시 뽑으면
  마음에 안 들었던 그 그림이 그대로 또 나온다.
- 시드는 **이름에서 유도한다.** 무작위로 뽑으면 같은 캐릭터를 다시 만들 방법이 없고,
  재현 테스트에서 "그때 그 그림"으로 돌아갈 수 없다.

## 6. 4단계 — 말풍선 합성

### 왜 모델에게 글자를 그리게 하지 않는가

한글을 제대로 쓰는 이미지 모델이 없기도 하지만, 더 큰 이유는 **글자가 픽셀이 되면 고칠 수 없다는 것**이다.
오타 하나에 다시 생성 비용이 든다. 그림과 글을 분리해 두면 대사 수정은 0크레딧이고,
이미 있는 캔버스 편집기가 그대로 동작한다.

### 왜 Sharp/PIL이 아니라 브라우저인가

합성은 `composeToonCut()`이 SlideDoc을 만들고 렌더 서비스(Playwright)가 그린다.
node-canvas로 따로 그리면 조판 규칙이 두 벌이 되고, 에디터가 보여 주는 것과 내보낸 이미지가
어긋나는 순간 신뢰가 깨진다. 이 프로젝트에서 그 원칙은 이미 검증됐다
([`05-DESIGN-SYSTEM.md`](05-DESIGN-SYSTEM.md)).

### 말풍선 = 도형 1 + 텍스트 1

전용 레이어 타입을 만들지 않았다. 텍스트 레이어여야 autoFit·충돌 검사·캔버스 편집이
전부 그대로 따라오기 때문이다. 새 타입을 만들면 `PanelCanvas`·`LayerInspector`·조판 엔진에
같은 로직을 한 벌 더 써야 한다.

스키마에 더한 것은 도형 role `'bubble'` 하나와 선택 필드 `tail` 하나뿐이다.

```ts
tail: { side: 'top'|'right'|'bottom'|'left', at: 0~1, size: px }
```

`at`이 픽셀이 아니라 비율이라, 비율 리사이즈에서도 꼬리가 화자를 계속 가리킨다.
꼬리는 CSS 삼각형으로 그린다 — 본체 배경색을 그대로 읽어 쓰므로 둘의 색이 어긋날 수 없다.

### 대비를 재지 않고 보장한다

카드뉴스는 배경 휘도를 실측해 글자색과 오버레이를 정한다. 인스타툰은 그러지 않고 **흰 띠를 깐다.**
컷마다 그림 밝기가 크게 달라서, 재서 맞추는 쪽이 "대체로 읽히지만 가끔 안 읽히는" 결과를 낸다.
띠를 깔면 대비가 구조적으로 보장된다.

### 도형 높이를 텍스트보다 먼저 잰다

도형이 먼저 그려지고 그 위에 글자가 얹히므로, 말풍선 높이를 미리 알아야 한다.
`measureBubbleText()`는 조판 엔진과 **같은 측정 함수·같은 제약**(`fitTextSize` + `approxMeasureFn`)을
쓴다. 그래서 나중에 `typesetSlide`가 다시 계산해도 같은 크기가 나온다.

## 7. 크레딧

| 항목 | 크레딧 | 근거 |
|---|---|---|
| `toonBase` | 6 | 스토리보드 호출 1회. 이야기가 짧아도 모델은 같은 공식을 읽는다 |
| `toonCut` | 2 / 컷 | 생성 이미지 1장 ≈ $0.025, 크레딧 1 = $0.05 → 4배 |
| `toonDerivedCut` | 5 | 다른 비율로 재조판. 그림과 대사는 이미 값을 치렀다 |
| `toonFormula` | 10 | 디자인 학습과 같은 호출 형태·같은 이미지 수 |

**9컷 = 6 + 18 = 24 크레딧 ($1.20).** 실비는 이미지 $0.225 + 모델 약 $0.05 = 약 $0.28 → **마진 4.3배.**
마진 하한은 3배다([`providerCost.ts`](../src/features/run/providerCost.ts)) — 렌더 호스트·스토리지·환불이
계산에 안 들어가 있기 때문이다.

카드뉴스 원본이 15인데 인스타툰이 24인 이유는 하나다: **스톡 사진은 검색이라 공짜고, 그림은 아니다.**
`providerCostUsd()`에 `generatedImageCount`를 더한 것이 그 사실을 마진 검사에 반영한 부분이다.
이걸 빼면 모든 인스타툰 실행이 거의 무료로 기록되고, 마진 검사가 가장 필요한 모드에서 무의미해진다.

`cutCount`는 견적 시점에 `run_items.toon`에 **얼려서** 저장한다. 공식에서 다시 읽으면,
차감 이후에 공식을 고친 사용자가 지불한 것보다 긴 편을 받는다.

## 8. 실패를 다루는 방식

| 무엇이 실패하면 | 어떻게 되나 |
|---|---|
| 컷 하나의 그림 | 그 컷만 그림 없이 선다. 대사·나레이션은 남는다. `art_failed:N:stage` 경고 |
| 캐릭터 시트 서명 | 앵커+시드만으로 계속 그린다. `reference_unavailable` 경고 |
| 스토리보드 | 1회 재시도 후 항목 실패 → 그 항목 크레딧만 환불 |
| 캐릭터가 남의 것 | 항목 실패 → 환불 |
| 첫 항목 실패 | 나머지를 버린다 (기존 규칙). 대개 원인이 같고, 다 실패시키면 시간과 제공사 비용만 든다 |

경고는 `toon_storyboards.warnings`에 남는다. 실패가 아니라 **사람이 봐야 할 것들**이다 —
장면 프롬프트가 외모를 다시 지정했다든가, 대사가 넘쳤다든가.

[`HANDOFF.md`](HANDOFF.md) §6의 교훈("조용히 틀리는 것이 가장 위험하다")을 여기서도 따른다:
일관성이 깨진 덱을 열었을 때 왜 깨졌는지가 값으로 남아 있어야 한다.

## 9. 엔지니어링 노트 — 다음 사람이 밟을 지뢰

### 일관성이 깨지는 다섯 가지 경로

1. **장면 프롬프트가 외모를 다시 묘사한다.** 가장 흔하다. `findIdentityDrift()`가 잡아 경고로 올린다.
   경고가 쌓이면 프롬프트의 나쁜 예를 늘려야 한다는 신호다.
2. **앵커를 매번 다시 조립한다.** 저장된 `anchor_prompt`를 쓰지 않고 `buildCharacterAnchor()`를
   런타임에 부르면, 항목 하나 편집이 과거 덱까지 소급된다.
3. **컷마다 시드를 바꾼다.** 다양성이 좋아 보여서 실수하기 쉽다. 시드는 캐릭터 것이지 컷 것이 아니다.
4. **참고 이미지 strength를 올린다.** 0.65 위로 가면 "같은 인물"이 먼저 무너진다.
5. **캐릭터를 편집한다.** 지금은 편집 경로가 없다(생성·삭제만). 편집을 붙일 때는 **새 버전**으로
   두어야 한다 — `template_versions`가 같은 이유로 그렇게 돼 있다.

### 저작권이 새는 두 가지 경로

1. **공식에 문장이 들어간다.** 40자 상한 + 종결어미 검사가 방어선이고, 화면에 경고를 띄운다.
2. **`notes` 필드에 캡션 전문을 붙여 넣는다.** 2000자까지 받는다 — 분석에는 쓰되 **저장하지 않는다.**
   저장 대상은 뽑아낸 공식뿐이다.

[`CLAUDE.md`](../CLAUDE.md) §5의 벤치마킹 가드레일과 같은 원칙이다: 참고는 "기능이 무엇을 해결하는가"
수준까지, 표현은 우리 것으로 새로 만든다.

### 조판이 어긋나는 세 가지 경로

1. **말풍선 도형과 텍스트의 제약이 달라진다.** 둘은 같은 `BUBBLE_FONT` 상수를 봐야 한다.
   도형 높이는 `measureBubbleText()`가, 텍스트 크기는 `typesetSlide()`가 계산하는데
   제약이 어긋나면 글자가 풍선 밖으로 나간다.
2. **가운데 앵커에 안쪽 여백을 더한다.** `middle-*`는 도형과 글자가 같은 선을 기준으로 접히므로
   여백을 더하면 오히려 세로 가운데에서 벗어난다.
3. **꼬리 방향을 바깥으로 준다.** 꼬리는 언제나 그림 안쪽(=화자)을 가리켜야 한다.
   `ANCHOR_TO_TAIL`이 그 매핑이다.

### 제공사

- **fal 응답을 통째로 신뢰하지 않는다.** `readFirstImage()`가 필드를 하나씩 확인한다.
  없으면 조용히 `undefined`가 흘러가 빈 카드가 되는데, 그때는 원인을 찾기 어렵다.
- **오류 본문을 로그에 옮기지 않는다.** 제공사 오류에 요청 프롬프트가 통째로 담겨 오는 경우가 있다.
- **`enable_safety_checker`를 끄지 않는다.** 인스타툰은 갈등을 다루므로 경계에 가까운 장면이
  나올 수 있고, 그 결과가 발행되는 계정은 사용자의 것이다.
- **`position: 'centre'` 크롭.** 스톡 사진과 달리 `'attention'`을 쓰면 말풍선을 놓으려고
  비워 둔 자리가 잘려 나간다.

## 10. 아직 안 한 것

- **실동작 검증.** `FAL_KEY`는 `.env.local`에 있지만 이 파이프라인으로 실제 호출한 적이 없다.
  라이브 하네스(`toonLive.test.ts`)를 아직 만들지 않았다 — 다른 기능들처럼 `RUN_LIVE_PIPELINE=1`로
  게이트해서 붙이는 것이 다음 순서다.
- **컷 하나만 다시 그리기.** `toon_storyboards.cuts`에 지시가 남아 있으므로 데이터는 준비돼 있다.
  `regeneratePanels`의 인스타툰 갈래를 붙이면 된다.
- **캐릭터 편집.** 지금은 생성·삭제만. 붙일 때는 버전으로.
- **보드에서 인스타툰 행.** `run_items.mode`가 이미 행 단위라 스키마는 준비돼 있고,
  시트 UI에 모드 열을 더하는 일만 남았다.
